Arabic Explorer

A standalone Arabic adaptation of System Explorer 7, sample 1, with 22 independent editions and a maximum depth of 65,536. All controls remain in English. Each HTML file includes its own styles, icons and program; no external library, font or server API is required.

Every expandable location, from the root through depth 65,535, offers exactly these 28 folders. At depth 65,536 the original terminal behavior is preserved: there are no deeper folders, but virtual files can still be created. Each non-root folder name is exactly one letter.

Unicode rules

The alphabet is constructed with Array.from and membership is checked against a fixed set, never a Unicode block or a contiguous character range. Folder validation accepts only the exact 28 code points above. Arabic digits, whitespace, punctuation, combining marks, extra Arabic letters, ligatures and presentation-form code points are excluded. Initial, medial, final and isolated glyphs are font shaping, not additional letters. Input is not compatibility-normalized into an accepted folder name.

Paths are arrays of letters in root-to-leaf order. Their canonical serialization is /ا/ب/ت/ي; / represents the root. UTF-8 HTML, JavaScript Unicode strings, IndexedDB structured cloning and UTF-8 JSON preserve the actual code points. File names use the original NFC normalization and a 255-code-point limit. File names can contain Arabic text and extensions; they are inserted using textContent. Slashes, backslashes, control characters, empty names and dot-directory names are rejected. A file cannot shadow an available child folder; duplicate file names are checked without case distinctions.

Right-to-left display and logical order

The English application layout, numbers and controls stay left-to-right. Arabic folder labels use RTL direction and bidi isolation. File-name inputs and file labels detect their own direction. Breadcrumb containers remain left-to-right, while each Arabic breadcrumb is individually isolated and RTL. This keeps root-to-leaf segment order stable. The address input and location summaries use an LTR bidi override: every path segment is one code point, so slash-separated segments stay in their logical order. CSS changes only display; it never reverses arrays or inserts directional marks into saved or copied paths. Arabic prose and multi-letter file names retain their natural RTL shaping.

Navigation and original features

  • Open a folder with its button or its Arabic letter key when focus is outside inputs and dialogs.
  • Enter a slash-separated Arabic path in the address bar and press Enter. Leading/trailing slashes and surrounding whitespace are accepted; invalid segments or excessive depth are rejected.
  • Back and Forward traverse session history. Alt+Left, Alt+Right, Alt+Up and Backspace retain the source shortcuts. Up removes the last segment; Home and Arabic drive return to the root.
  • Breadcrumbs show at most the last 24 path components. At large depths the ellipsis opens Jump to level, accepting any earlier level including root level 0.
  • Grid/list views, depth indicator, progress bar, terminal screen, accessibility announcements, reduced-motion support and responsive layout are preserved.
  • New file creates a virtual name-only file. It contains no executable content. Files can be created at any depth, including the final level.
  • The menu retains New game, Delete files, Share website and About. New game clears only this sample's saved position and files. Delete files supports selection and Select all in the current folder. Both destructive actions retain the original password 1111; this is a confirmation mechanism, not encryption or access security.
  • Share website uses native sharing where available, otherwise a copy-link dialog. It shares the current sample URL without saved data. About shows the sample's Program ID.

Search and path copying

Search this folder filters the visible child folders and current folder's files by Unicode substring, with NFC normalization for matching. It does not change the fixed alphabet or saved contents. Clear the search field to see all entries. It is a local filter, not an exhaustive search of the enormous implicit tree. Copy path writes the canonical Unicode path to the clipboard, with the source program's selection/manual-copy fallback.

Saving, recovery and export

Position, view preference and virtual files are automatically saved in IndexedDB on this browser and origin. Successful navigation commits its saved state before changing the displayed location. Files are indexed by canonical folder path and name; only the current folder's files are loaded during ordinary browsing. Transactions keep file creation, deletion and resets atomic. Quota and access failures are reported; inaccessible saved data is not silently discarded. The retry notice and database version-change handling remain available.

Each sample has one unique 16-hex-digit storage key. Its IndexedDB database name is that same key; its legacy localStorage key is also that key. All 44 Program IDs and storage keys are mutually distinct. No original Explorer database is accessed. The original legacy migration code is retained: valid legacy data under that sample's own key is migrated transactionally; the old data is removed only after commit. Invalid migration data stays unchanged. Browser storage is scoped by origin and browser profile; a file:// copy and an HTTPS-hosted copy may have different saves. Clearing browser data deletes local saves.

Export save downloads arabic-explorer-save.json containing format: "arabic-explorer-30", version: 1, the path array, listMode and all virtual file records. Unicode letters remain ordinary JSON strings. Export explicitly loads all saved files, so its memory requirement scales with the backup size.

Import save validates the format, depth, alphabet, file names, folder paths and duplicate names before any write. A confirmation asks whether to replace the selected sample's saved position and all files. The replacement is a single transaction. Invalid input leaves existing data intact. Importing a backup into another sample is an explicit transfer; the samples never share live databases. Backups contain no Program ID or storage key and cannot redirect storage. They are unencrypted and include file names and paths.

Mathematical background and memory use

The system is an implicit rooted 28-ary tree of height D = 65,536. Root depth is 0. There are 28^d folders at depth d; paths of length d are words over the 28-letter alphabet. The total number of folder nodes including the root is Σ(d=0…D) 28^d = (28^(D+1) − 1) / 27. The number of terminal paths is 28^65536, an integer with 94,841 decimal digits. The program never enumerates these counts or constructs the tree.

Give each letter a digit from 0 through 27 in the documented order. For a fixed depth, a path's zero-based rank is Σ(i=1…d) digit[i] × 28^(d−i). Leading zero digits are meaningful because depth is part of the path. Number and ordinary floating-point arithmetic cannot represent these ranks exactly at large depths; a theoretical exact calculation would require BigInt. Navigation needs only code-point arrays, not huge integer ranks.

The active path uses O(d) memory and a canonical string has 2d UTF-16 code units for nonempty paths (all alphabet letters are BMP characters). At maximum depth that is 131,072 code units, approximately 256 KiB for a two-byte character representation, excluding engine overhead. Rendering creates at most 28 child folder buttons and 24 named breadcrumbs, plus the current folder's files. No recursion depends on path depth.

History uses persistent parent-linked nodes. Unchanged path prefixes are shared between history entries, avoiding the quadratic memory growth caused by retaining a complete array at every successive level. A simple descent to depth d creates O(d) history nodes; visiting new branches adds their new suffix nodes. Converting a history entry to an active path and path validation take O(d) time. As in the source, Back/Forward history is session-only; reloading restores the saved position and view, not previous history. Export/import scale with the number and total sizes of stored records.

Validation

The accompanying test.cjs runs all 22 samples in headless Chromium through Playwright on a temporary local HTTP server. Run node explorer/30/test.cjs with Playwright installed and Chromium available at /usr/bin/chromium. This test server and automation are development tools; the HTML files do not depend on them.

The checks cover exact alphabet order, 44 unique 16-hex identifiers, identical implementations, invalid Unicode path rejection, Arabic-key navigation, path entry, RTL/LTR CSS direction, Unicode file names, view/position/file persistence, local search, clipboard copying, JSON export/import, depth 65,535 and 65,536, terminal navigation, bounded breadcrumbs, live cross-sample storage isolation, shared history prefixes, Jump to level, and the original password-protected deletion/reset flows. Browser errors fail the run. Desktop and narrow-screen screenshots are generated in the operating system's temporary directory. These automated checks exercise Chromium; platform fonts and clipboard permissions may differ in other browsers.
